Introducing Castor: A Secure Microkernel for LLM Agents

March 6, 2026 · 5 min read
Substrate Labs
Castor Team

LLM agents that autonomously invoke external tools are becoming ubiquitous. But the frameworks that power them — LangChain, CrewAI, AutoGen — provide no security boundary between the LLM and the outside world. If an agent can call a tool, it can call it without limit. If it runs too long, it forgets its own instructions. If it hits a dangerous operation, there's no systematic way to pause and ask a human.

Castor is a microkernel that fixes this. It interposes a deterministic execution engine between the LLM and external tools, providing capability-based budgets, checkpoint/replay, and human-in-the-loop control in a single coherent system.

The Problem​

We've been building LLM agents for production use and kept hitting the same three failure modes:

Privilege abuse. An agent with file access decides to "clean up" and deletes production data. The framework has no concept of budgets — if the tool is registered, the agent can call it without restriction.

Resource exhaustion. An agent asked to "research thoroughly" makes 3,000 API calls in an hour. There's no depletable budget, no cost tracking, no way to set spending limits.

Context amnesia. After a long conversation, the agent forgets its own safety instructions because they've been pushed out of the context window.

These aren't edge cases. They're the default behavior of autonomous agents.

The OS Analogy​

We noticed something: the relationship between an LLM and external tools is structurally identical to the relationship between a user-space process and the operating system kernel.

OS ConceptCastor Analog
User/kernel spaceLLM vs. execution engine
System callsTool invocations via proxy.syscall()
CapabilitiesDepletable budget tokens
Process schedulingCheckpoint/replay with HITL
Virtual memory pagingContext window management

This isn't just a metaphor — it's a structural mapping. The trust boundary is real.

What Castor Provides​

1. Capability-Based Security​

Tools declare what they consume. The kernel enforces budgets:

from castor import Castor, castor_tool, SyscallProxy

@castor_tool(consumes="api", cost_per_use=1.0)
async def web_search(query: str) -> list[str]:
    return [f"Result for '{query}'"]

@castor_tool(consumes="finance", cost_per_use=50.0,
             destructive=True, requires_hitl=True)
async def execute_trade(symbol: str, amount: float) -> dict:
    ...

kernel = Castor(tools=[web_search, execute_trade])
cp = await kernel.run(agent, budgets={"api": 100.0, "finance": 5000.0})

When the budget runs out, the agent gets structured feedback — not a crash:

"Insufficient capability 'api': need 1.0, have 0.5 remaining."

The LLM reads this and adjusts its plan.

2. Checkpoint/Replay​

You can't pickle Python coroutines. Castor doesn't try. Instead, it records every completed tool call in a replay journal. Suspend raises an interrupt; resume replays from the top with cached responses.

Run 1:
  web_search(...)    -> executes, logs result
  execute_trade(...) -> destructive! SuspendInterrupt raised
  Checkpoint saved.

Human approves.

Run 2 (replay):
  web_search(...)    -> cached (instant)
  execute_trade(...) -> HITL approved, execute live
  Agent completes.

This single mechanism gives us HITL, crash recovery, and preemption — all for free.

3. Human-in-the-Loop​

Dangerous tools suspend for human review. Humans can:

  • Approve — execute the tool as requested
  • Reject — cancel with feedback ("Don't delete those files")
  • Modify — provide guidance ("Only delete files older than 30 days")

Castor never mutates the agent's arguments. On modify, the LLM receives feedback and re-plans. This preserves replay determinism.

4. Preemptive Scheduling​

asyncio.Task.cancel() injects a CancelledError at the next await point. Since LLM streaming has an await at every chunk boundary, the kernel can preempt an agent at token-level granularity — typically 10-100ms. No shielded sections needed; the fast/slow path split handles double-execution risk.

5. Context Window Management​

The MMU subsystem monitors token usage, pins system prompts (never evicted), and removes stale messages via FIFO when the context window fills up. Agents can retrieve evicted memories with search_memory.

Framework Integration​

Castor works standalone or as a guard layer for existing frameworks. We've built proven integrations with:

  • smolagents — override execute_tool_call() to add budget + HITL
  • pydantic-ai — wrap WrapperToolset.call_tool() with budget + HITL

Both integrations add Castor's guarantees without changing agent code.

Current Status​

Phase 1 is complete:

  • 368 tests, 0 lint errors
  • All core requirements implemented (Gate, Scheduler, MMU, Capability)
  • Sync + async multi-agent spawning with budget delegation
  • Token-level LLM preemption with proportional budget
  • castor.lib — agent developer standard library with tool(), chat(), react(), supervisor(), and more
  • Expanded CLI: castor run, castor ps, castor inspect, castor reject, castor modify

What's Next​

Phase 2 introduces castord, an seL4-inspired Rust daemon that replaces the original PyO3 plan. The kernel becomes a pure state machine with zero I/O, communicating via dedicated protocols (AISA for agents, ATSP for tools, MCP bridge for compatibility). You'll still import castor in Python — castord runs as a sidecar.

Roche is our companion project for sandbox orchestration. Castor controls what agents intend to do; Roche controls what processes can do (Docker, Firecracker, WASM isolation with AI-optimized defaults). They're independent — no code dependency — but designed to work together.

We're also exploring distributed agent orchestration where checkpoints are the portable unit of execution across nodes.
